# devix セキュリティ対策整理

営業資料・LP「セキュリティへの取り組み」スライド作成用

最終更新：2026年10月14日

## 1. このファイルの目的

devixの営業資料・LPで、セキュリティへの取り組みを誠実かつ分かりやすく説明するための基礎資料。
実装済みの対策、追加確認が必要な項目、今後の対応を分け、未確認の機能を実装済みと誤って説明しない。

## 2. 対外説明の基本方針

-   課題を羅列して不安を与えるより、「情報を必要最小限にする設計」「アクセス制御」「通信の保護」「データ保全」の軸で説明する。
-   「セキュリティ万全」「完全に安全」「不正アクセスを完全に防止」など、保証と受け取られる表現は使わない。
-   JSON形式でデータを受け渡すこと自体を、SQLインジェクション対策として説明しない。安全性は、サーバー側の入力処理とデータベースへのアクセス方法で決まる。
-   バックアップの自動取得・保存状況・復元テストが確認できるまでは、「バックアップ体制を確立済み」と表現しない。
-   実装確認が終わった項目だけ、具体的な対策として対外説明に加える。

## 3. これまでの開発記録で確認できる対策

### HTTPSによる通信の暗号化

-   本番サイトでHTTPSを利用している。
-   対外説明候補：「HTTPSによる通信の暗号化」

### ログイン認証・セッション管理

-   FastAPI側でセッション情報を管理する構成。
-   ブラウザには`session_id`をHttpOnly Cookieで保持し、バックエンド側のセッションを認証状態の基準とする設計。
-   バックエンドのセッション情報には、ユーザーID、病院ID、ロール等のほか、Supabaseのアクセストークン・リフレッシュトークンを保持する構成の開発記録がある。
-   `session_id`、アクセストークン、リフレッシュトークンは役割が異なる。JWTはトークン形式の一つであり、トークンを使っていることだけで安全性が保証されるわけではない。
-   JWTを採用しているか、各トークンの有効期限・更新・失効方法、Cookieの`Secure`・`SameSite`設定などは、認証フローと本番設定を確認してから対外説明する。

### 病院ごとのデータ管理

-   データベース設計に`hospital_id`を利用し、病院ごとにデータを区分する設計。
-   SupabaseのRLS（Row Level
    Security）やロールに基づくアクセス制御を実装した記録がある。
-   全API・全テーブルのポリシーが現在も適切か、他院データへのアクセスを拒否できるかは検証が必要。
-   対外説明候補：「病院ごとのデータ管理とアクセス制御」

### ユーザー・病院の利用停止

-   `users.is_active`および`hospitals.is_active`を利用し、無効なユーザー・病院のログインを拒否する仕組みを実装した記録がある。
-   既存セッションの失効や全APIでの権限再確認は要確認。

### 個人情報を必要最小限にする設計

-   devixは医療機器の配置・状態管理を主目的とし、電子カルテとの連携を必要としない。
-   患者名は任意入力項目であり、個人情報を一切扱わないわけではない。
-   対外説明では「個人情報を原則として必要最小限に抑える設計」「患者情報の入力は必要最小限とする運用を推奨」などと表現する。

## 4. 優先して対応・確認する項目

### A. SQLインジェクションなどの入力処理

-   JSONで受信した値は、正常に解析されれば文字列等のデータとして扱われる。しかしJSON形式だけでSQLインジェクションを防げるわけではない。
-   Supabaseクライアントの通常のテーブル操作を利用している箇所、SQL文字列を直接組み立てる箇所、RPC・独自SQLの利用箇所を確認する。
-   SQLを直接組み立てる場合は、パラメータ化クエリを使用する。
-   FastAPI/Pydanticで入力値の型、長さ、許容値、形式を検証する。
-   GASの問い合わせ受付処理は、Next.js
    APIからJSONをGASへ渡し、Googleスプレッドシートやメール処理につなぐ構成。通常はSQLを直接実行しないため、SQLインジェクションとは分けて考える。
-   GAS側では、入力検証、秘密キー検証、スプレッドシートへの数式注入、表示時のXSS等を確認する。
-   コード確認・必要な修正・テストが終わるまでは、「SQLインジェクション対策済み」と断定しない。

### B. データベースのバックアップ・復元

-   SupabaseのDBデータを定期的に保全する仕組みを整備する。
-   バックアップの取得頻度、保存先、保持期間、アクセス権限、取得失敗時の確認方法を決める。
-   可能であれば本番DBとは分離した保管先を使用する。
-   復元テストを実施し、実際に復旧できることを確認する。
-   自動取得と復元確認が完了するまでは、「定期バックアップを実施済み」「復旧体制を確立済み」と表現しない。

### C. APIの認可・病院間データ分離

-   各APIでログイン状態、ロール、病院IDを検証する。
-   リクエストの`hospital_id`や機器IDを書き換えても、他院データを取得・変更できないことを確認する。
-   SupabaseのService
    Roleキーを利用する処理では、RLSに依存しきらず、バックエンド側の認可チェックを確認する。
-   全API・全テーブルを確認するまでは、完全な分離を保証する表現は避ける。

### D. 秘密情報の管理

-   Supabase Service Roleキー、GAS秘密キー等をサーバー側だけに保持する。
-   `NEXT_PUBLIC_`環境変数に秘密情報を含めない。
-   GitHub、ビルド成果物、ログへの混入がないことを確認する。

### E. ログ・保守

-   重要な変更操作や管理者操作の監査ログ、ログイン失敗の検知状況を確認する。
-   依存パッケージの脆弱性確認と更新手順を整備する。
-   上記の実装状況は、現時点では確認が必要。

## 5. LP・営業資料に掲載する文章案（現状向け）

### セキュリティへの取り組み

devixは、医療機器の配置・状態管理に必要な情報に機能を絞り、個人情報の取り扱いを原則として最小限に抑える設計を採用しています。

-   **通信の暗号化**：HTTPSによる通信
-   **アクセス管理**：ログイン認証とユーザー権限に基づく管理
-   **病院ごとのデータ管理**：病院単位でデータを区分する設計
-   **情報管理への配慮**：電子カルテとの連携を必要としないシンプルな構成

医療機関での利用を想定し、必要な情報への適切なアクセスとデータの保護に配慮したシステム設計を行っています。

注：掲載前に、本番環境でのHTTPS、アクセス制御、病院間データ分離の動作を確認する。確認が済んでいない項目は、断定を弱めるか掲載を保留する。

## 6. 病院からの質問に対する回答方針

### 他院からデータを見られませんか？

病院ごとのデータ管理とアクセス制御を採用しています。認証・権限管理とデータベース側のアクセス制御を組み合わせ、他院の情報にアクセスできないようにする設計です。
※全API・全テーブルでの検証後に、より強い断定表現を使用する。

### 患者情報を扱いますか？

devixは医療機器の配置・状態管理を目的としており、電子カルテとの連携を必要としない設計です。患者名は任意入力項目ですが、個人情報の入力は必要最小限とする運用を推奨しています。

### ログイン情報や認証トークンはどのように管理していますか？

devixでは、バックエンド側でセッション情報を管理し、ブラウザにはHttpOnly Cookieを利用してセッション識別情報（`session_id`）を保持する構成を採用しています。認証状態やユーザー権限をサーバー側で確認する設計です。

※JWTの利用有無、Cookieの`Secure`・`SameSite`属性、セッション有効期限、ログアウト時の失効、アクセストークン・リフレッシュトークンの保管・更新方法は、実装と本番設定を確認したうえで説明する。営業資料では技術用語を必要以上に強調せず、実際の構成に即して回答する。

### バックアップは取っていますか？

バックアップの自動取得と復元手順を整備し、データ保全を進めています。
※実際の取得・保存・復元テストが完了したら、実施頻度や復旧手順など、確認済みの内容を説明する。

### SQLインジェクションなどの攻撃への対策は？

入力値の検証やデータベースへの安全なアクセス方法を確認・整備しています。
※コード確認とテストが完了したら、実際に採用した方法に沿って説明する。

## 7. 営業資料の説明を強化する段階

1.  **現状**：HTTPS、ログイン認証、権限管理、病院別のデータ管理について、実際の本番設定を確認して説明する。
2.  **入力処理の確認後**：入力値検証、安全なDBアクセス、GAS側の入力処理を確認し、検証済みの対策を追記する。
3.  **バックアップ整備後**：取得頻度、保管先、保持期間、復元テストの結果を説明できるようにする。
4.  **アクセス制御の検証後**：他院データへのアクセス拒否、一般ユーザーと管理者の権限分離を検証した範囲で説明する。

## 8. 避ける表現

確認や根拠がない限り、次の表現は使わない。

-   「セキュリティは万全です」
-   「不正アクセスを完全に防止します」
-   「個人情報は一切扱いません」
-   「SQLインジェクション対策済み」
-   「バックアップ体制を確立済み」
-   「第三者機関による安全性の認証を取得済み」
